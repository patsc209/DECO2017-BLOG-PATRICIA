Hello fellow reader! After weeks of planning, wireframing, and designing the database, week 9 was the first time SEAblings (we decided to change the name from Bubble -> SEAbling: South East Asian Siblings) started to feel like an actual website rather than a collection of diagrams. The shift from planning to building is always a bit of a reality check. Things that seemed straightforward on a wireframe turn out to need more thought once you're actually writing the code.

<b>Getting dummy data in</b> 
The first thing we needed before we could build or test anything meaningful was data. An empty feed and an empty map tell you nothing about whether the design is working, so we seeded the database with dummy data generated by AI. Double checking the dummy data recipes were correct with the ingredients was actually a useful exercise in its own right. It forced us to be concrete about what a recipe record actually contains, and we caught a couple of gaps in the schema that hadn't been obvious from the ERD alone. The cuisine tag field, for example, needed to be more constrained than we'd originally planned. Freeform text would make filtering unreliable, so we settled on a fixed set of values early.

<b>Building the map</b>
The ingredient map was the feature I was most invested in getting right, partly because it's the thing that makes SEAblings different from any other recipe site, and partly because it was the most technically uncertain part of the build. And after some intensive research, I found that an interactive map with community-pinned locations has more steps than I thought.

I used Leaflet.js for the map itself, which sits cleanly alongside HTMX without replacing it. The map renders on page load, and ingredient filter interactions are handled via HTMX requests that update the pin layer without a full page reload. That felt like the right division of responsibility: Leaflet owns the map, HTMX owns the filtering interaction.

Getting the first pins to appear on the map from real database records rather than hardcoded coordinates was a satisfying and cool moment. 

<b>Conclusions and learnings</b>
A few assumptions from the planning phase didn't survive contact with the actual build. The relationship between ingredients, pins, and stores made complete sense in the ERD but required more careful thought when writing the actual queries. Specifically, pulling together an ingredient name, store name, suburb, and coordinates into a single map response without making redundant database calls. It's a small thing but it's exactly the kind of thing that only becomes visible when you're writing real code against a real schema.

The dummy data also made the feed look more alive than expected, which gave us confidence that the card grid layout from the wireframes was the right call. Three columns on desktop, each card showing a thumbnail, recipe name, and cuisine tag, works well once there's actual content filling it. Got to add some colour and character next though, looks quite depressing being B&W.
